## Bugs confirmés

**1. `marketing_recommendations` a un flux de revue sans endpoint pour le faire avancer**
(`db.py:1977-1992`, `app.py:1587-1600`). La table créée cette semaine (commit `440959a`) porte
`review_status CHECK(... IN ('review','accepted','rejected'))`, `reviewed_by`, `reviewed_at`,
`reject_reason` — une file de validation complète. Mais `app.py` n'expose que
`GET /api/marketing-recommendations` (lecture) et `POST /api/marketing-agent/run` (écriture par
l'agent) : aucun `POST .../accept` ni `.../reject`, contrairement au couple qui existe pour
`vocabulary-candidates` (`app.py` a bien `/api/vocabulary-candidates/{id}/accept` et `/reject`).
Preuve : `grep -n "marketing_recommendations" app.py db.py` ne retourne aucune route d'écriture
de décision ; comparer avec `grep -n "vocabulary-candidates" app.py` qui en a deux. Une
recommandation entre en `review` et n'a aucun moyen d'en sortir. C'est exactement le défaut que
`audit_veille.md` §3.2/§5.G documentait déjà pour cinq autres files (« le schéma anticipe une
gouvernance que l'API ne permet pas d'exercer ») — la même erreur vient d'être reproduite sur une
sixième table, la semaine même où elle a été créée.
*Correctif proposé* : `POST /api/marketing-recommendations/{id}/accept|reject`, même contrat que
`vocabulary-candidates` (`reviewed_by`, `reject_reason` typé). Environ 20 lignes, sur le modèle
déjà présent dans `app.py`.

**2. Trois endpoints créés cette semaine ne sont appelés nulle part dans le front**
(`/api/marketing-dossier`, `/api/marketing-agent/run`, `/api/marketing-recommendations`).
Preuve : script Python comparant chaque route `@app.*` de `app.py` aux littéraux présents dans
`static/app.js` et `static/js/*.js` — les trois ne matchent aucune occurrence, ni dans `app.js`
(3757 lignes) ni dans `static/js/{api,explorer,export,ui}.js`. Ce n'est pas forcément une
régression : `feedback-dossier`, `market-sizing`, `reference-matrix`, `vocabulary-candidates`,
`actor-candidates` et `/api/sources` ne sont pas appelés non plus et sont antérieurs — l'app
semble avoir une convention assumée de « dossiers »/files de revue pilotés par API directe
(curl) plutôt que par UI. Mais rien ne documente cette convention (pas de README, CLAUDE.md ne
mentionne pas ces endpoints), et pour un outil à plusieurs sessions concurrentes, un endpoint
sans aucun appelant connu dans le repo est indiscernable d'un endpoint mort ou oublié. À classer
en dette de documentation plutôt qu'en bug — voir « Usage de Claude Code » ci-dessous.

   audit — voir « À vérifier »). Un test sur le modèle des trois existants fixerait la preuve
   dans le code plutôt que dans l'historique git uniquement.

## Usage de Claude Code

- **Aucune collision détectée cette semaine** : les 22 commits sont cohérents avec leur message,
  chaque changement JS est accompagné de son CSS quand il en fallait un (`b00ae26` : `app.js` +
  `offers.css` + `market_compilation.py` ensemble), aucune fonction ajoutée sans appelant, aucun
  commit « restaure/réintègre ». Le worktree + la discipline `git status` avant commit (ajoutées
  au CLAUDE.md le 28/09) semblent tenir.
- **CLAUDE.md est à jour** avec le code réel : la commande de boucle de vérification correspond
  exactement à `.github/workflows/ci.yml` (ruff → mypy → pytest, mêmes trois commandes), le
  script `scripts/new_worktree.sh` existe et correspond à la description, et la correction du
  01/10 sur `data/*.db`/WAL (`d99c6a8`) est cohérente avec `db.backup_all_databases()` qui
  alimente réellement `data/backups/` avant chaque run (`app.py:2290`, `rejudge_offers.py`,
  `prune_off_topic_sources.py`, `backfill_match_terms.py`) — donc l'instruction « interrogez une
  copie de `data/backups/` » reste valable même si la sauvegarde planifiée Windows a été
  abandonnée le même jour.
- **Proposition concrète** : ajouter au CLAUDE.md la convention citée au point 2 ci-dessus
  (dossiers API-only). C'est le seul écart réel trouvé entre CLAUDE.md et le code cette semaine,
  et il est trivial à combler.
- **Proposition concrète** : pour les futures tables de revue (prochain candidat visible : toute
  nouvelle file créée par une session), ajouter une checklist d'une ligne dans CLAUDE.md —
  « une colonne `review_status` s'accompagne toujours d'au moins un endpoint accept/reject dans
  le même commit » — puisque c'est la deuxième fois (sur six files recensées par l'audit v3) que
  ce couplage est oublié. Un test générique (parcourir les tables avec `review_status` et vérifier
  qu'une route `{queue}/{id}/accept` existe) attraperait la classe entière d'un coup ; mentionné
  dans la feuille de route (§5.G.1, file de revue unifiée) mais pas encore fait.
