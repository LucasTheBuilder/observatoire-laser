## Environnement (pas un bug applicatif)

Même symptôme que le 05/10 → 16/11 : le premier `pytest` échoue avec `ModuleNotFoundError: No
module named '_cffi_backend'` sur `test_sitemap_pdf_ingestion.py` (3 échecs, chaîne `pdfplumber`
→ `pdfminer` → `cryptography` → binding Rust `_cffi_backend` absent). Autre particularité de cet
environnement précise cette semaine : `python3`/`python` pointent vers `/usr/bin/python3.11`
(symlink), alors que `pip`/`pip3` par défaut installent dans les site-packages de `python3.13` —
`pip install -r requirements.txt ...` sans précision laisse `python3 -m pytest` sans aucun module
installé. Contournement : `python3 -m pip install -r requirements.txt -r requirements-dev.txt`
puis `python3 -m pip install cffi`, qui installent bien dans l'arbre de `python3.11` que `python3`
résout — ensuite `pytest` repasse à `944 passed, 354 subtests passed` en ~71 s. `ruff check .` :
« All checks passed! ». `mypy .` : « Success: no issues found in 128 source files » (notes
`annotation-unchecked` informatives, préexistantes, non bloquantes). Rien à corriger côté dépôt ;
le symlink python3→3.11 est une particularité du conteneur d'audit, pas du projet (CLAUDE.md cible
Windows/`py`), donc non reportée comme point ouvert — juste consignée ici pour que la prochaine
exécution ne reparte pas de zéro si `pip install` seul semble « réussir » sans rien installer où
`python3` le cherchera.
